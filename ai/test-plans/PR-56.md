Floor = `rfc.constants.DEFAULT_TIMEOUT` = **5400s** (verified: `constants.py:3`; the test also asserts this literal so floor and client default cannot silently diverge). Every static `Test Timeout` / `[Timeout]` across `core/robot/**` (variables `${…}`/`%{…}` excluded as runtime-resolved):

Minimum non-excluded value = 6000s > 5400s floor. **Invariant holds for every LLM-driven suite.**

## Deviations — are they sound?

- **Literal 50× on 90s–5min suites** — yes. 50× of the de-facto default (120s→6000s) and the 3/4/5-min variants lands at 100–250min, all comfortably above the 90-min HTTP budget. Sound.
- **Capped 3h ceiling (180min) on the 15min/30min suites** — yes. These two already make many sequential LLM calls (consistency: N_RUNS=5 + judge; HF defect batch: 10 items), so a literal 50× (12.5h / 25h) is absurd for a dev-box pre-flight. Capping at 180min keeps them well above 5400s while bounded by ~N×(90-min budget). Sound.

## Exclusions — correct?

The 5 docker **code-execution** suites (`docker/{python,c,bash,rust,shell}/__init__.robot`) are listed in `EXCLUDED_SUITES` and kept small (90s–3min). Verified each: their `Test Timeout` bounds deterministic container command execution, not an LLM call — a hang there *should* fail fast; their LLM pre-flight runs in Suite Setup, which `Test Timeout` does not cover. The `docker/llm/` suite (a real LLM suite) is correctly NOT excluded (250min). Container-exec/Playwright timeouts are `${…}`-variable or `networkidle timeout=30s` and are outside the static-parse net. **Exclusions correct.**
